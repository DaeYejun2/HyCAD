# 2026-10-23 Ubuntu 확장 검증 기록

대상 변경은 catalogue·front-end LIVE 추적, 저장 캡처 자동/수동 재생, 두 Grafana 대시보드와 Ubuntu 실행 경로다. 아래에는 이번 작업에서 **실제로 확인한 결과와 아직 수행하지 않은 시험**을 구분한다. 한 시점의 판정이나 기능 시험을 공격 확인·탐지 성능·장시간 운영 안정성으로 확대 해석하지 않는다.

운영 릴리스 소스는 `e160145d6ee6`이며, 애플리케이션 이미지는 `4f78484` 소스의 실행 코드와 일치함을 확인했다. 이후 문서 갱신 커밋과 운영 중인 애플리케이션 버전은 별도로 관리한다.

질의 성공은 운영 데이터소스에서 해당 질의를 처리했다는 의미다. 모든 시간 범위에 데이터가 존재하거나 모든 캡처의 모든 창을 검증했다는 의미는 아니다. 코드·규칙 시험 통과를 재부팅·장시간 운영 시험 통과로 해석하지 않는다.

## 2. VM 수집과 LIVE 판정 확인

실제 수집 스트림의 **600,000개 이벤트**를 확인했으며 JSON 파싱 실패는 **0개**였다. 다음 **8개 컨테이너 이름**이 실제 입력에서 관측됐다.

| 서비스 | 관측한 컨테이너 |
|---|---|
| catalogue | `docker-compose_catalogue_1`, `docker-compose_catalogue_2`, `docker-compose_catalogue_3`, `docker-compose_catalogue_4` |
| front-end | `docker-compose_front-end_1`, `docker-compose_front-end_2`, `docker-compose_front-end_3`, `docker-compose_front-end_4` |

이는 설정 파일에 이름이 존재한다는 확인과 구별되는 **입력 이벤트 관측 결과**다. 그 자체가 모든 창의 완전성·정상 판정·탐지 정확도를 보장하지는 않는다.

두 서비스의 원본 창 종료 시각이 `1792752360`인 LIVE 결과를 확인했다. 이는 **2026-10-23 10:46:00 UTC / 19:46:00 KST**이며, 아래 내용은 이 창의 스냅샷이다.

| 서비스 | 모델 분류 | 확인한 근거 |
|---|---|---|
| catalogue | 정상 (`normal`) | 해당 LIVE 창의 모델 결과 |
| front-end | 전체 이상 의심 (`all_infection`) | A 임계값 대비 비율 초과 없음, 4개 레플리카 모두 B > 6.05007, C = 0.45820697 > 0.2 |

front-end는 A 초과 없이 B와 C 조건을 함께 만족해 **전체 이상 의심**으로 분기했다. 저장 Node 10 자료에서 관측한 drift와 달리, 이 LIVE 창에서는 C도 초과했다. 내부 코드의 `all_infection` 명칭은 감염 확인을 뜻하지 않는다. 이 창만으로 공격 여부나 Node 버전·트래픽·연결 정책 중 어느 것이 원인인지 확정할 수 없다.

수동 재생을 일시정지·재개한 19:46~19:53 KST 확인 구간에도 두 LIVE 서비스의 원본 창 시각은 각각 **420초**, 처리 창 수는 **18→32로 14창** 진행했다. 수동 재생을 멈춰도 LIVE 판정은 계속됨을 이 구간에서 확인했다.

VM의 실제 설치 위치는 다음과 같다.

- 수집 래퍼: `/usr/local/libexec/hycad-sysdig-catalogue`
- 수집 감독기: `/usr/local/libexec/hycad-serve-capture.py`
- 컨텍스트 래퍼: `/usr/local/libexec/hycad-context-catalogue`
- 컨텍스트 조회기: `/usr/local/libexec/hycad-serve-context.py`

기존 래퍼 이름은 유지하면서 수집 대상을 catalogue·front-end로 확장했다. 이 확인 과정에서 새 공격을 실행하지 않았다.

## 3. 저장 캡처의 재판정 결과

Ubuntu에서 저장 캡처를 UTC 30초 창으로 집계하고 고정 기준선으로 다시 평가했다. Node 4/10 파일은 각각 61창 중 첫·끝 불완전 창을 제외한 59창이 아래 유효 창이다.

| 캡처 ID | 유효 창 수 | 모델 분류 |
|---|---:|---|
| `frontend-node4` | 59 | normal 59 |
| `frontend-node10-drift` | 59 | drift 59 |
| `catalogue-normal` | 199 | normal 199 |

Node 10 캡처의 첫 유효 창에서 관측한 근거:

| 값 | 관측 | 해석 |
|---|---|---|
| A | 4개 레플리카 모두 0 | 동료 간 A 초과 없음 |
| B | 약 7,606~7,863, 기준 약 6.05007 | 기준선 대비 구성비 차이로 B 조건 충족 |
| C | 약 0.11334, 기준 0.2 | C 초과 없음 |

따라서 A 침묵·B 초과·C 안정이라는 **정상 변화 의심(drift)** 분기를 만족했다. 현재 front-end 컨테이너의 Node 10.24.1 확인과, Node 4 과거 정상 참조 사용 사실은 별도 환경 근거다.

이 결과는 **저장 캡처의 재판정**이다. 현재 LIVE가 계속 drift라고 판정한다는 결과도, Node 버전 변경만이 원인이라는 인과 증명도 아니다. 파일·시나리오 이름을 공격의 정답으로 자동 사용하지 않았으며, 정상 참조를 자기 기준선으로 평가한 normal 건수를 독립 FPR·정확도 측정으로 사용하지 않는다.

## 4. 자료 반입과 재생 입력 검증

원본 보관 경로는 `/var/snap/docker/common/hycad/captures/source/Grafana_caps`다. 재생에 사용하는 승인 catalog·캐시·기준선은 `/var/snap/docker/common/hycad/captures/approved`이며 `HYCAD_CAPTURE_DIR`는 후자를 가리킨다. 원본을 재생 컨테이너에 직접 마운트하지 않는다.

| 확인 | 결과 |
|---|---|
| VM 원본과 운영 호스트 사본의 SHA-256 대조 | 원본 파일 **65개 모두 일치** |
| 승인 catalog 로딩 | **15개 모두 성공**: catalogue 13개, front-end 2개 |
| 승인 캡처별 실행 | **15개 모두 첫째·둘째 창 처리 확인** |
| 수동 제어 화면의 승인 선택 목록 | **15개 표시** |

첫째·둘째 창 처리는 입력 로딩과 창 진행을 확인하는 시험이며, 불완전한 창을 유효 판정으로 바꾸지 않는다. 전체 반복 주기의 장시간 실행 검증이나 모든 캡처의 공격 라벨 검증을 뜻하지 않는다.

원본·캐시·기준선 해시와 품질 통계는 보호된 메타데이터와 catalog에서 관리한다. 공개 문서에 원본 시스템콜·명령행·서비스 로그·자격 증명을 복사하지 않는다.

자동 재생의 원본 전체 범위·진행률·순환 횟수는 현재 메인 대시보드에 표시하지 않는다. 화면에는 원본 창 종료 시각과 입력·기준선 정보가 표시되며, 수동 제어 화면에서 해당 작업의 진행 상태를 확인한다.

## 6. 운영 상태와 미실시 시험

| 확인 | 결과 또는 한계 |
|---|---|
| Prometheus 수집 인스턴스 | LIVE 2개·자동 재생·수동 재생의 **4개 모두 UP** |
| 운영 systemd 서비스 | **5개 모두 active/enabled** |
| 설명 로그 전달 오류 누적값 | 기동 초기 누적 **8건**, 수동 제어·LIVE 진행 확인 구간에서 **8→8로 증가 없음** |
| 실제 호스트 재부팅 | **미실시** |
| 물리적 네트워크 연결 단절·복구 | **미실시** |
| 코드 보관의 버전 대응 | 공개 발행 트리는 위 운영 실행 코드와 동일하며, 문서·참고 자료를 추가한다. 비공개 사본과 Mac 복구용 번들·소스 아카이브의 커밋 및 해시는 별도 백업 기록으로 남긴다. |

`active/enabled`는 확인 시점에 서비스가 실행 중이고 부팅 시 시작하도록 설정됐다는 뜻이다. 재부팅이나 실제 네트워크 단절 후 자동 복구를 실험으로 입증했다는 뜻은 아니다. 전달 오류 누적값 역시 0이 아니므로, 증가가 없다는 관측을 모든 과거 설명의 전달 성공으로 해석하지 않는다.

front-end 사건에서 전후 이벤트 압축 파일·연결 목적지 JSON·서비스 로그와 컨텍스트가 실제 생성됐고, 보존 파일 해시와 9개 컨테이너의 컨텍스트 조회 성공을 확인했다. 전후 파일은 각각 128MiB 상한을 유지하며 상한에 도달한 사례는 `limited`로 표시됐다. 최근 확인 사례에서는 이상 구간을 포함한 사전 요청 90초 중 약 45초 분량, 사후 요청 60초 중 약 54초 분량만 포함됐고 `truncated=true`, `boundary_coverage=false`였으므로 **60초 전후 자료의 완전한 보존을 보장하지 않는다.**

구현 계약은 [아키텍처](architecture.md), 운영 절차는 [서버 운영](server-operations.md), 시연 순서는 [발표 가이드](presentation-runbook.md)를 참고한다.
